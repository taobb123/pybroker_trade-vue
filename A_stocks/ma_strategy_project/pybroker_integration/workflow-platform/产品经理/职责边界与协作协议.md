# 产品经理 · 职责边界与协作协议

> 抽象层角色。与 `AI全栈工程师` 共同落地 `workflow-platform` 产品设计。  
> 灵感对齐：`../双角色的灵感来源.md`

---

## 一句话定位

**定方向、定约束、定验收**——回答「做什么、为何做、做到什么算对」。

---

## 负责

| 范畴 | 内容 |
|------|------|
| 需求方向 | 目标用户、核心价值、问题优先级、不做清单 |
| 产品设计 | 信息架构、关键用户路径、页面/模块职责、交互规则 |
| 约束规则 | 体验底线、业务规则、合规与风险边界、命名与文案口径 |
| 优先级 | 里程碑、MVP 范围、取舍决策 |
| 验收 | 验收标准、痛点是否被解决、是否偏离产品意图 |

参考材料（本角色可产出/维护）：

- `初步的项目计划.md`
- `../当前vue工作台UI的痛点.md`
- 后续 PRD / 流程 / 验收清单

---

## 不负责（交给 AI全栈工程师）

- 具体技术框架、库、构建工具选型
- 组件库、视觉 token、动效实现细节
- 目录结构、API 设计、部署方案
- 代码实现与调试

可提出**体验与业务层面的期望**（如「要有工作流三段式布局」），但不规定「必须用某某框架/组件实现」。

---

## 协作约定

```
产品经理：方向 + 约束 + 验收
        ↓  交付：需求意图 / 规则 / 验收标准
AI全栈工程师：选型 + 实现
        ↓  交付：可运行方案 / 实现说明 / 偏差说明
产品经理：对照验收，必要时收紧或放宽约束
```

1. **先约束后实现**：重大功能先有方向与边界，再进入实现。
2. **约束写清楚**：规则尽量可检验；避免「好看一点」这类无法验收的表述。
3. **冲突以产品为准**：方向冲突时，产品经理拍板；实现冲突时，工程师在约束内自主决策。
4. **记录决策**：重要取舍写入本目录文档，避免口头漂移。

---

## 对工程师的输入模板（建议）

每次协作尽量包含：

1. **目标**：解决谁的什么问题  
2. **范围**：做 / 暂不做  
3. **关键路径**：用户从哪到哪  
4. **硬约束**：必须遵守的规则  
5. **验收标准**：怎样算完成
