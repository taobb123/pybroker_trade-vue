## A. 产品经理发言

### 1. 阶段判断

已具备：工作流运行、配额、高级策略、支付会员壳、报告导出。  
进入：**MVP 商业闭环验证**——验证「为什么来 → 为什么用 → 为什么付费 → 为什么留下」。

**明确不做（MVP）**：堆更多策略 / 页面 / 图表 / 模型。

### 2. 优先级（工期无关）

| 优先级 | 模块 | 星级 | MVP 是否必须 |
|--------|------|------|----------------|
| P0 | 用户身份 + 数据归属（users 根表） | ★★★★★ | **必须** |
| P1 | 支付后权益自动化（订单↔会员↔配额已绑定到 user_id） | ★★★★☆ | **必须**（相对现状：从本地 Mock 升到服务端归属） |
| P2 | 首次体验 Onboarding（5 分钟内第一次价值） | ★★★★★ | **必须** |
| P3 | 行为事件 / 转化漏斗 | ★★★★★ | **必须（最小事件集）** |
| P4 | 管理员后台（查人/单/改会员/加额度） | ★★★★☆ | **MVP 薄做** |
| P5 | 安全：run 限流 + 支付异常态 | ★★★☆☆ | **MVP 薄做** |

### 3. MVP 验收闭环（用户故事）

```
注册/登录（有 user_id）
  → Onboarding 选身份 + 推荐策略 + 赠送体验次数
  → 运行基础策略（计配额，归属该用户）
  → 触达限额 / 高级策略 → 升级提示
  → 支付成功 → 会员与配额自动生效
  → 导出报告（Pro）
  → 事件可统计漏斗（访问→注册→运行→付费）
  → Admin 能查单并手工纠偏
```

### 4. 硬约束

1. 一切可计费/可审计行为必须带 `user_id`（禁止继续以 guest 作为收费验证主路径）  
2. 不新增策略功能面；只补「身份 / 归属 / 转化 / 纠偏」  
3. 行为分析先做**事件表**，不做完整 BI 产品  
4. Onboarding 目标：5 分钟内第一次成功运行  

### 5. 请工程师回应

- 逻辑数据模型（最小表）  
- 与现有 `businessRules` / 支付 API 的衔接  
- MVP 实现切片顺序（按优先级，不写工期）

## B. AI全栈工程师回应

### 1. 现状缺口

| 能力 | 现状 | 缺口 |
|------|------|------|
| 登录 | localStorage Mock | 无 users 库、无服务端会话 |
| 配额/会员/订单 | 浏览器本地 + 支付 JSON 文件 | 未强制 user_id 归属 |
| 支付回调形状 | ✅ simulate | 需写入 users/membership |
| 行为漏斗 | 用量页 Mock 访问 | 无 events |
| Onboarding | 无 | 无 |
| Admin | 无 | 无 |

### 2. 选型（约束内）

| 项 | 决策 |
|----|------|
| DB | SQLite（MVP）→ 可迁 PostgreSQL；单文件便于本机 |
| Auth | 邮箱+密码哈希（MVP）；微信等后置；废弃 guest 作为付费主路径 |
| 会话 | 服务端 session / JWT（任选其一，推荐 JWT） |
| 事件 | 同库 `events` 表，同步写入关键动作 |
| Admin | 同应用 `/admin` + `role=admin` 种子账号 |

### 3. 默认假设（待产品确认后执行）

1. MVP **强制登录后才能 run**（将 `ENFORCE_AUTH_FOR_RUN=true`）  
2. Onboarding 赠送 **+3 次** 体验配额（记入独立 `bonus_quota`，当日有效）  
3. 最小事件：`page_view` / `run_strategy` / `export_report` / `click_upgrade` / `payment_success`  
4. Admin 仅本机种子账号，不做完整 RBAC  
5. 退款：**MVP 不做自动退款**，仅 Admin 手工降档
