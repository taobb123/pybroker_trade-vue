## B. MVP 闭环验收对照（用户故事）

```
注册/登录 → Onboarding → 运行计配额 → 升级 CTA → 支付生效 → 导出 → 漏斗 → Admin
```

| 环节 | 状态 | 说明 |
|------|------|------|
| 注册/登录（users + JWT） | ✅ 已闭环 | 服务端库；非早期 localStorage Mock。UI 仍残留「Mock 登录验收壳」文案 |
| Onboarding + bonus+3 | ✅ 已闭环 | 路由强制首登引导 |
| 运行归属 + 配额扣减 | ✅ 已闭环 | `ENFORCE_AUTH_FOR_RUN=true`；服务端 consume |
| 限额 / 高级门控 → 升级 | ✅ 已闭环 | Free 挡 advanced；导出挡 Free |
| 支付 → membership 自动生效 | 🟡 **形状闭环，钱未闭环** | 下单入库 + simulate-pay 写 membership；**无真收款** |
| 报告导出 Pro | ✅ 已闭环 | 预览可看，复制/下载门控 |
| events 漏斗 | ✅ 最小闭环 | `/usage` 上方真漏斗；下方访问趋势仍 Mock |
| Admin 纠偏 | ✅ 薄做闭环 | 改会员 / 加额度 / 订单标记 |

**判定：** 对「内部演示 / 邀请测试」可交付；对「公开消费用户付费」——支付脚手架未拆，**不可正式收款上线**。

## G. 工程侧已确认事实（便于拍板）

1. M1–M6 代码与规则表已对齐；商业形状在服务端，不再是纯前端 localStorage 真相。  
2. 支付成功路径在代码里固定为：`create` → **`simulatePaymentPay`** → `apply_membership`。  
3. 微信/支付宝在 UI 上「看起来像渠道」，后端 `mode` 仍是 simulate。  
4. 这是**故意留的脚手架**（纪要 002 / R5「真机替换点」），不是偶然 bug——但对消费用户等价于「假装修」。
